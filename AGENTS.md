# food-delivery

Сервер Cook API для заказа и доставки обедов. Стек проекта — Node.js 20 (версия в Dockerfile), TypeScript со строгой типизацией, Express, Knex и MySQL 8.0. Используй npm и сохраняй согласованность `package.json` и `package-lock.json`.

## Структура проекта

- `src/app.ts` собирает Express-приложение через `createApp()`. Запуск слушателя и фоновых задач находится в `src/index.ts`. Сохраняй возможность поднять приложение в тестах без запуска фоновых задач.
- Добавляй HTTP-маршруты в соответствующий файл `src/routes/*.routes.ts`. Общий роутер `src/routes/index.ts` подключается под `/api`.
- Размещай обработчики и логику конкретного запроса в `src/controllers/`. Переиспользуй функции из `src/utils/` и middleware из `src/middleware/`. Фоновые задачи следуют структуре `src/services/`.
- Используй `src/db/knex.ts` для доступа к БД, а внутри транзакции выполняй связанные запросы через её объект `trx`.

## Контракт API и доступ

- Типы строк БД находятся в `src/models/`, поля используют `snake_case`. Типы HTTP-запросов и ответов находятся в `src/dto/`, поля используют `camelCase`. Преобразуй строки БД в DTO и сериализуй даты через `src/utils/dateMapper.ts`, учитывая допустимость `null`.
- Валидируй параметры пути, query и тело до записи в БД. Ожидаемые ошибки обработчиков передавай через `AppError` и `next(error)` в общий `errorHandler`. Сохраняй HTTP-статусы, коды и форму ошибок, на которые опираются клиенты.
- Для защищённых маршрутов используй `authenticateToken`, затем `checkRole`, если маршрут ограничен по ролям. Проверяй доступ к конкретной компании или заказу в обработчике. Переиспользуй `hasCompanyManagementAccess` для проверки доступа менеджера к своей компании и администратора к любой компании.
- Сохраняй существующие проверки активного пользователя и сессии, лимиты запросов авторизации и ограничения загрузок при изменениях соответствующих маршрутов.
- При изменении поведения эндпоинта синхронизируй обработчик, DTO, аннотацию `@swagger` рядом с маршрутом и контрактные тесты. OpenAPI доступен по `/api-docs/openapi.json`. При изменении контракта, который использует `fast_lanch`, проверь совместимость с клиентом.

## База данных и бизнес-правила

- Меняй схему новой миграцией в `migrations/` с временной меткой и функциями `up` и `down`. Учитывай существующие строки при добавлении обязательных полей, уникальных индексов и других ограничений. Сверяй актуальную схему со всей цепочкой миграций.
- Сохраняй семантику мягкого удаления через `deleted_at`. В обычных выборках активных сущностей используй `whereNull('deleted_at')`. Для истории и проверки наличия заказа за день соблюдай правила соответствующего эндпоинта.
- Храни денежные суммы в целых центах. Сохраняй снимки цены и категории позиций заказов. При изменении состава, стоимости доставки или скидки пересчитывай суммы и распределение оплаты в той же транзакции. Переиспользуй расчёты из контроллера заказов и `src/utils/orderBilling.ts`.
- Определяй границы бизнес-дня и день недели через `src/utils/businessTime.ts`. Часовой пояс задаёт `BUSINESS_TIME_ZONE`, по умолчанию `Europe/Moscow`. Используй тот же бизнес-день для дневного лимита заказов и отчётов за сегодня.
- Сохраняй ограничение одного заказа пользователя на бизнес-день, включая уже отменённый или мягко удалённый заказ этого дня. Учитывай существующую блокировку при создании заказа и уникальность `(user_id, order_day)` в БД.
- При правках редактирования заказов сохраняй проверку статуса `created` и срока приёма заказов рейсом. Проверяй переданный `expectedItemsRevision` в транзакции под блокировкой заказа и обновляй `items_revision` при изменении состава.
- Сохраняй ограничение одной привязки рейса на компанию в `route_companies`. При изменении статуса заказа сохраняй запись в `order_status_history` в той же транзакции.

## Локальный запуск и проверки

- Команды проекта определены в `package.json`. Для установки зависимостей используй `npm ci`, для локального запуска — `npm run dev`, для проверки сборки — `npm run build`. Параметры окружения смотри в `example.env`, `knexfile.js` и коде. Храни реальные секреты в локальном окружении.
- После изменений TypeScript запускай сборку и подходящий набор `npm run test:<module>`. Доступны `smoke`, `notifications`, `auth`, `companies`, `catalog`, `routes`, `orders` и `reports`. Для прогона всех наборов используй `npm test`.
- Пиши проверки на `node:test` и `node:assert/strict`. Для HTTP-тестов используй `tests/helpers/test-server.ts`, для тестов с демоданными — `lockAndSeedDb` и `releaseDbTestLock` из `tests/helpers/db-test-lock.ts`. Добавляй проверки изменённого контракта в соответствующий файл `tests/contracts/`.
- Запускай тесты только с отдельной локальной тестовой MySQL. Даже `test:smoke` применяет миграции через `tests/index.test.ts`, а интеграционные тесты используют `seeds/01_demo_data.ts`, который очищает таблицы. Перед запуском проверь, куда указывают `DB_HOST` и `DB_DATABASE`.
